Per-Space Important Webpages

Going to a project's desktop and instantly pulling up the webpages that belong there — Comms = LinkedIn + Gmail + a few others — opened, deduped, and ready.

2026-06-21 topic: per-space-webpages focus: quickly open a Space's important webpages mode: repo-grounded

Is it even possible? (short answer)

Yes — and the core of it is small. The product already has the exact seam: bringUpApps() switches to a project's Space and opens its blueprint apps, skipping anything already open. Opening that project's webpages is a sibling of opening its apps. The whole design tension is one asymmetry:

That asymmetry is why "elegant" splits into two bets — a zero-permission path that ships immediately, and a smarter path that reads tabs once you grant Automation. Both are below. Nothing here requires the brittle "restore my exact live session" that the product already ruled out of identity; this is a curated/captured set of a project's pages, which is on-identity with the app blueprint.

✓ Validated on-device (2026-06-21). Tested live on this Mac (Chrome): a raw open <url> bounces the tab to wherever the browser already has a window — it does not land on the desktop you're standing on. The reliable mechanism is a dedicated per-project browser profile, opened only after the Space switch is verified: a profile with no window open elsewhere has its window born on the current desktop. Confirmed on two desktops; the one failed attempt was pure timing (fired before the switch completed). A shared/default profile fails precisely in the case that matters — when the target desktop has no browser window yet. Full write-up: docs/solutions/integration-issues/macos-per-space-url-opening-needs-windowless-browser-profile.md. This promotes idea 6 from a nice-to-have to the load-bearing enabler.

Recommended framing → idea 8 (manual launcher). The cleanest answer isn't to force windows onto the right Space at all — it's a per-Space reminder you click while you're already there. Clicking on the Space opens the page on the Space, no programmatic switching to race and no permission needed; per-project profiles (idea 6) stay only as the empty-Space fallback. This fits the product's "remind me, not teleport me" identity and sidesteps the macOS wall instead of hacking around it.

Grounding Context

Product. Parallel Project Desktops — a native macOS (Swift/SwiftUI) menu-bar app where each macOS desktop (Space) is a named project, keyed by stable Space UUID. Surfaces: the menu-bar dropdown list, a ⌃⌥Space Spotlight-style search panel, a transient resume card, and a morning recap.

What a project holds today. A Project (Project.swift) carries a Blueprint = app bundleIDs + passively-recorded window frames (recorded but not acted on — the seam for future layout-restore). There is no web-URL concept yet.

Capture. saveCurrentDesktopAsProject / updateApps (AppModel.swift) read the apps open on the active desktop via AppInspector.appsOnCurrentDesktop() and store their bundle IDs — no config form; you capture what's open.

Boot. bringUpApps(project) (AppModel.swift:243) is the explicit "Bring up apps here" action: switch to the Space, launch blueprint apps not already windowed here, skip duplicates, report apps stuck on another desktop. enter() is switch-only by design.

Prior product decisions. Resume is "remind me, not teleport me"; restoring an exact browser tab / in-app state is explicitly outside the product's identity; auto-learning a project's app-set from usage was deferred; ~7–10 project cap; the app already requires Accessibility + the macOS switch-to-Desktop shortcuts.

macOS feasibility. Opening a URL is trivial and permission-free (and can target a specific browser/profile). Reading currently-open tabs needs per-browser AppleScript with a one-time Automation (TCC) grant — Safari/Chrome/Brave/Edge support it, Arc partially, Firefox not at all.

Verification note. Bases are grounded in code read directly during this run (AppModel.swift, Project.swift, AppLauncher.swift) and in standard macOS platform behavior. The optional fresh-context basis-verifier pass was skipped to keep this run fast; the macOS scripting/profile claims should be spike-confirmed before committing (esp. Arc tab enumeration and Safari profile selection).

Topic Axes

  • Capture / authoring — how URLs get into a project (snapshot open tabs, manual add, paste, learn-from-use, import).
  • Open & boot — how URLs open on entering/booting (which browser, ordering, focus, window grouping).
  • Link model — what a "link" is (bare URL vs named/typed entry, grouped sets, per-project browser profile, app+web unified).
  • Surfacing / UI — how the user sees and triggers it (menu submenu, ••• menu, search panel, recap).
  • Reliability / edge — browser support, login/account state, Automation permission, duplicate avoidance, staleness.

Ranked Ideas

Jump to:
  1. Web links join the blueprint, opened by the existing boot action
  2. Ship open-only first — a zero-permission v1
  3. A link is a named, ordered, browser-targeted entry (a "destination")
  4. Snapshot the open tabs when you save a desktop
  5. Reconcile, don't blast — dedupe links against open tabs
  6. Per-project browser profile — the right account, automatically
  7. Surface it: a per-project links submenu + type-to-open in the search panel
  8. Per-Space page reminder + click-to-open — the manual launcher (recommended)
1

Web links join the blueprint, opened by the existing boot action

open & bootConfidence 90%Complexity Medium
Description
Extend Blueprint with an ordered list of links and teach bringUpApps to open each URL (via NSWorkspace.open / open -a) right after it launches the apps — same single action, now restoring both the apps and the pages. An optional "anchor" page opens focused so the Space boots into the work rather than onto a random frontmost tab, and a one-line result strip reports only what failed.
Axis
open & boot
Basis
direct: bringUpApps (AppModel.swift:243) is already the explicit "set up this desktop" loop with dedupe; NSWorkspace.open opens a URL with no permission. Opening pages is the same primitive as launching apps.
Rationale
The user's verbatim ask — "go to a desktop and quickly pull up all the important webpages and open them" — is literally the boot action they already invoke, minus the URLs. Reusing it means one verb to learn, not two.
Downsides
Needs the link data model (idea 3) to exist first; without dedupe (idea 5) re-running spams duplicate tabs. The anchor/focus refinement is per-browser AppleScript, so keep it best-effort. Placement constraint (validated): open URLs only after the switch engine confirms the Space landed, and into the project's own browser window — which requires idea 6, since a browser already windowed on another desktop can't be made to open here.
2

Ship open-only first — a zero-permission v1

reliability / edgeConfidence 85%Complexity Low
Description
Sequence the work so v1 requests no new permission at all. Authoring is manual to start — paste a URL, "add this page," or a "save the current tab" command — and opening uses permission-free open. The Automation (tab-reading) grant is deferred until the user explicitly opts into snapshot-capture (idea 4) or dedupe (idea 5), prompted at the exact moment its value is obvious.
Axis
reliability / edge
Basis
direct: grounding — opening needs no permission; reading tabs needs an Automation grant and fails on Firefox. reasoned: just-in-time consent grants higher than upfront; the app already spends two permission asks (Accessibility + shortcuts), so a third on first run risks the activation funnel.
Rationale
Decoupling "open" (always works, every browser) from "read" (best-effort, scriptable browsers) guarantees the headline promise never fails — and it aligns with the existing "remind me, not teleport me" identity. This is the cheapest path to the user actually having the feature.
Downsides
Manual authoring is more friction than auto-snapshot until idea 4 lands; some users will want the snapshot on day one.
3

A link is a named, ordered, browser-targeted entry — a "destination"

link modelConfidence 80%Complexity Low–Medium
Description
Model a link as a typed entry { url, title, browser? } rather than a bare string, stored as a parallel field on Blueprint (alongside bundleIDs, exactly as frames enriches a bundle ID). The menu shows "LinkedIn", not the raw URL; order is preserved; a link can pin to a specific browser. Leave the door open to generalize "url" into "destination" later (a Linear board, a Figma file, an obsidian:// deep link) without a schema rewrite.
Axis
link model
Basis
direct: Blueprint (Project.swift:13) already pairs bundleIDs with a structured frames map — a typed link array is the same shape. external: deep-link schemes (slack://, obsidian://, things://) are real and openable via the same call, so the entry generalizes cleanly.
Rationale
This is the one-way-door decision: the JSON schema and every UI that reads it depend on it. Get the entry type right once and groups, per-project profiles, and destinations all become cheap; get it wrong (bare strings) and the menu is unreadable and the model has to be migrated.
Downsides
Risk of over-generalizing into a "universal launcher" — keep v1 to {url, title, browser?} and treat destinations as a noted extension, not scope.
4

Snapshot the open tabs when you save a desktop

capture / authoringConfidence 75%Complexity Medium
Description
Mirror how apps are captured: when the user hits "Save this desktop" / "Update apps," also read the currently-open tabs of any scriptable browser on that desktop and store their URLs as suggested links. No form — you arrange your Comms desktop once, save, and LinkedIn + Gmail are now part of the project. Crucially this reads tabs only at authoring time, never on every boot, so it doesn't drift into the rejected "teleport me" behavior.
Axis
capture / authoring
Basis
direct: capture today (AppModel.swift:158/:196) reads open apps with zero config; grounding confirms open tabs are readable via per-browser AppleScript with one Automation grant for Safari/Chrome/Brave/Edge.
Rationale
Manual URL entry would betray the product's "you capture what's open, no config" philosophy. Snapshot-capture is the only authoring model consistent with how the app already works — and it spends the Automation grant once, for authoring, not on the hot path.
Downsides
Per-browser scripting + an Automation prompt; Firefox can't be read and Arc only partially. Pairs with idea 2: snapshot is the opt-in upgrade over the zero-permission baseline.
5

Reconcile, don't blast — dedupe links against open tabs

reliability / edgeConfidence 70%Complexity Medium
Description
Before opening a project's URLs, read the target browser's current tabs and open only the ones missing (normalizing URLs — strip tracking params, trailing slash, www); focus an existing tab instead of spawning a second. Re-running boot becomes idempotent and safe — the Space converges to its intended page set rather than accumulating duplicates.
Axis
reliability / edge
Basis
direct: bringUpApps (AppModel.swift:259/:275) already encodes a "skip what's already windowed here, never duplicate" contract for apps — links must honor the same promise or feel broken. reasoned: URL normalization for matching is standard.
Rationale
Duplicate-tab spam is the single fastest way a "open my pages" feature becomes annoying enough to disable. The codebase already treats no-duplication as a core promise; extending it to links is what makes the action habitual.
Downsides
Dedupe requires reading current tabs (the Automation grant + per-browser logic); when unavailable (Firefox, ungranted), fall back to dumb open and say so once.
6

Per-project browser profile — the mechanism that makes Space placement work (validated)

link modelConfidence 90%Complexity Medium–High
Description
Bind each project to a dedicated browser profile (Chrome --profile-directory). This is the load-bearing enabler, not just a convenience: a profile with no window open elsewhere has its new window born on the desktop you're on, which is the only reliable way to get a project's pages onto the project's Space. It also delivers per-project identity for free — Comms opens the personal Gmail, Sales the work Gmail, no manual account-switching.
Axis
link model
Basis
direct: validated on-device 2026-06-21 (see solutions doc) — a fresh-profile --new-window opened on the current desktop on two separate Spaces; a raw open on the shared profile bounced to where Chrome already had a window. external: Chromium accepts --profile-directory launch flags. reasoned: the profile having no window elsewhere is exactly what avoids the "can't place a window on another Space" wall.
Rationale
This is what answers "will it work?" When the target desktop has no browser window yet — the case the user was rightly worried about — a shared/default profile cannot be forced to open there. A dedicated profile can, because there's no twin window elsewhere to get pulled to. Per-project login isolation is the bonus on top.
Downsides
Per-browser launch-flag matrix; cleanest on Chromium (Chrome/Brave/Edge) — Safari 17+ profiles have no clean CLI selection, Firefox uses -P. One profile per project means logging in once per profile. Residual edge: if the user manually drags a project's profile window to another desktop, the bounce returns — detect "profile window not on this Space" and warn / reopen.
7

Surface it: a per-project links submenu + type-to-open in the search panel

surfacing / UIConfidence 75%Complexity Medium
Description
Two surfaces, reusing what exists. (a) A "links" submenu under each project row in the menu-bar dropdown — hover "Comms" to reveal LinkedIn, Gmail, etc., each openable individually, plus "Open all here." (b) Index every project's links in the ⌃⌥Space search panel so typing "gmail" or "Comms↵" resolves to "switch + open the pages" as one keyboard command. The list shows what would open; the panel does it.
Axis
surfacing / UI
Basis
direct: both the menu-bar list and the ⌃⌥Space Spotlight panel already exist as surfaces. reasoned: the ask is an action ("quickly pull up… and open them"), not a browsing task — a keyboard-first open beats hover-and-click, and a submenu makes a project's pages glanceable even from another desktop.
Rationale
The slowest part of pulling up a project page is the navigation overhead (find desktop → find browser → find tab). A fuzzy search-to-open collapses that to two keystrokes; the submenu cures the "which pages mattered for Comms again?" forgetfulness.
Downsides
Expands the search panel's scope from project names to project contents — a real product-surface decision — and adds menu depth. Scales to a searchable index if a project ever has many pages.
8

Per-Space page reminder + click-to-open — the manual launcher (recommended framing)

surfacing / UIConfidence 90%Complexity Low–Medium
Description
Instead of auto-forcing windows onto the right Space, show each project's important pages as a click-list on surfaces that already exist — the menu-bar project row, the resume card, the morning recap, the ⌃⌥Space panel: [LinkedIn] [Gmail] [Open all]. You click while you're on the Space, and the page opens there because you have focus. A reminder + launcher, not an auto-restore.
Axis
surfacing / UI
Basis
direct: validated on-device 2026-06-21 — sitting on a desktop that already had its own Chrome window, a plain open opened the tab in that local window, no bounce. Opening a URL is permission-free and works in every browser; the resume card and morning recap already exist as surfaces. reasoned: the bounce only occurs when the app switches Spaces and places windows programmatically — keeping the human on the Space at click time removes that whole failure mode and the switch-timing race we hit during testing.
Rationale
This fits the product's own "remind me, not teleport me" identity and sidesteps the macOS window-placement wall instead of hacking around it. In the common case it needs no Automation permission, no per-project profiles, and no global-setting change — it just opens the page into the browser window already on the Space you're standing on. It's the synthesis of ideas 1, 3, and 7, reframed as manual rather than automatic.
Downsides
If the current Space has no browser window, a plain click still opens wherever the browser lives (the bounce) — but as a visible, intentional action, not a silent failure. The clean fallback is to open the project's dedicated-profile window (idea 6), born here because you're here. So: manual launcher in the common case, profile fallback for empty Spaces.
